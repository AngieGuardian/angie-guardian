# Hot-path allocation baselines for `make bench-regress` (also a CI job).
#
# Each line: <benchmark name> <maximum allocs/op>. The gate runs the named
# benchmarks at a FIXED iteration count (-benchtime 10000x) and fails if any
# exceeds its baseline. ns/op is deliberately not gated: CI machines are too
# noisy for it.
#
# ONLY benchmarks whose allocation count is genuinely deterministic belong
# here, which in practice means: no background goroutines. A benchmark that
# spawns them charges their allocations to its own count, and how much work
# each one batches depends on the scheduler, so the number moves with core
# count and load. BenchmarkChallengeIssue is the worked example and is
# deliberately NOT gated: it drives CounterCache, whose drain goroutines make
# it swing between 28 and 36 allocs/op purely with GOMAXPROCS (it failed CI at
# 36 against a baseline of 35 measured locally). It stays a profiling
# benchmark; BenchmarkIssue gates the deterministic core of that same path.
# Before adding an entry, check it holds steady across `GOMAXPROCS=1,2,4,8`.
#
# When a change legitimately adds an allocation to a hot path, raise the
# baseline in the same commit and say why in its message. When a change removes
# allocations, lower the baseline so the win is locked in.
